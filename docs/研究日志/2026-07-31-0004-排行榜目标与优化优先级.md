# 排行榜目标与优化优先级

日期：2026-07-31

## 本次结论

本次只读研究了官网总榜和总榜前 12 名玩家的公开 profile，没有启动游戏，没有修改正式存档。已将 50 个可计分主线关卡的近最佳目标写入 `examples/leaderboard-targets.json`。

官网说明总榜分数为各关能耗的 `log2` 之和，且分数越低越好。在其他指标不变时，任何一关能耗减半都会使总分减少 1：

- 组件关：`energy = gate * delay`
- 程序关：`energy = gate * delay * cycle`
- 总榜：`sum(log2(level_energy))`

因此，不能只看延迟。延迟减少但门数大幅增加时，可能不会提高总榜成绩。本项目同时保留三个代表目标：最低能耗、最低延迟、最低门数。

## 抓取方法

数据源：

- 总榜：<https://turingcomplete.game/leaderboard>
- 玩家 profile：`https://turingcomplete.game/profile/{id}`
- 单关榜：`https://turingcomplete.game/leaderboard/{level_id}`

采样 profile ID：`362, 834, 92, 3972, 2525, 3963, 390, 6238, 141, 423, 3794, 871`。

单关榜页面通常达到数百 KB，全量抓取 50 关会产生不必要的负载。本次改为抓取总榜前 12 名的 profile，每次请求间隔约 1 秒。这些 profile 一次公开显示全部程序关成绩和组件关 Pareto 前沿，最终覆盖了 50/50 个可计分关卡。

这些数值是“公开顶尖玩家样本中的最佳或近最佳”，不是经过 50 个单关榜全量遍历证明的绝对世界纪录。后续准备提交排行榜前，再对重点关卡进行定点复核即可。

## 优化优先级

下表仅对当前 `examples/manifest.json` 中已有非零基线的关卡计算。“理论收益”为 `log2(baseline_energy / sampled_target_energy)`，可近似理解为达到样本目标后对总榜的分数降幅。

| 关卡 | 当前能耗 | 样本目标 | 当前延迟 -> 低延迟目标 | 理论收益 |
| --- | ---: | ---: | ---: | ---: |
| `byte_less_u` | 11760 | 246 | 98 -> 4 | 5.58 |
| `byte_less_s` | 11760 | 246 | 98 -> 4 | 5.58 |
| `overture_alu_2` | 56610 | 1200 | 102 -> 6 | 5.56 |
| `signed_negator` | 5508 | 120 | 51 -> 3 | 5.52 |
| `decoder_3` | 948 | 42 | 12 -> 3 | 4.50 |
| `byte_adder` | 10752 | 515 | 96 -> 4 | 4.38 |
| `overture_conditions` | 1500 | 76 | 15 -> 3 | 4.30 |
| `counter` | 14732 | 816 | 58 -> 8 | 4.17 |
| `overture_alu_1` | 2795 | 231 | 13 -> 3 | 3.60 |
| `binary_programming` | 298288 | 39969 | 206 -> 3 | 2.90 |
| `byte_equal` | 700 | 152 | 14 -> 4 | 2.20 |
| `full_adder` | 128 | 28 | 8 -> 3 | 2.19 |
| `byte_lsr` | 918 | 210 | 9 -> 3 | 2.13 |
| `symphony_alu` | 56610 | 16840 | 102 -> 9 | 1.75 |
| `bit_inverter` | 20 | 6 | 4 -> 2 | 1.74 |

第一批应优先处理 `byte_less_u`、`byte_less_s`、`overture_alu_2`、`signed_negator`、`decoder_3`、`byte_adder`。这些关卡既有显著延迟差距，也有最大的总榜潜在收益。已经达到或接近样本前沿的简单关卡不应占用早期时间。

## SchematicHub 与公开电路

官方客户端中可确认以下信息：

- 内置 API 地址为 `https://turingcomplete.game/api`，实际 POST 路径为 `/api/`。
- 客户端包含 `req_list_schematics`、`req_download_schematic`、`req_upload_schematic` 等请求类型。
- 列表响应字段包含 `category`、`name`、`user_id`、`username`、`description`、`votes`、`download_count`、`image_data`、`upload_time`、`size`。
- 游戏的分享界面链接 CC0，表明通过 SchematicHub 分享的电路是预期可公开复用的资源。

但当前没有发现可供外部程序直接使用的公开文档或 JSON API：

- `GET https://turingcomplete.game/api/` 返回 `405 Method Not Allowed`，只允许 POST。
- 对 `/api/` POST 普通 JSON `{}` 返回 `400 Bad Request`。
- 客户端使用内部 `serialize_server_request` / `deserialize_server_response` 序列化，协议尚未实现。
- 官网 leaderboard 和 profile 页面只链接分数，不提供电路文件或 SchematicHub ID。

可合法参考的公开资源：

- <https://github.com/zoickx/turing-complete>：CC0-1.0，包含 1792 个树节点。有 `byte_adder/Low-Delay`、`signed_negator/Optimized`、`conditions/Clever`、`architecture/ASIC/DIVMOD`、`HANOI`、`MAZE`、`MOD4`、`NIM`、`SORT` 等可作为电路结构参考的公开方案。主分支最新提交为 2024-02-29，存档格式与 2.1.281 的直接兼容性不能假定。
- <https://github.com/LukeGrahamLandry/TuringCompleteSchematicArchive>：作者明确说明内容来自 0.1059 beta 的 SchematicHub，上传时采用 CC0。当前树共 1107 项，主要是旧版 architecture 和 component factory 电路，适合架构研究，不能当作新版主线关卡的可直接写回方案。
- <https://github.com/Stuffe/save_monger>：游戏生产环境使用的存档读写源码，CC0，后续可用来校对存档编解码。

其他 GitHub 上的存档仓库大部分没有明确 license，可以用于人工研究，但不应直接并入本开源项目。

## 后续行动

1. 先对优先级前 6 的关卡进行逻辑等价综合，以样本的低延迟点为上界、低能耗点为主榜目标。
2. 对标记为 Pareto 多点的关卡保留多个 candidate，不应只保留一个“延迟最低”方案。
3. 在准备写回正式存档前，用单关榜对当前 candidate 邻近的世界纪录做定点复核。
4. SchematicHub 协议应作为独立研究项，不应阻塞当前的离线电路生成和存档写回。
