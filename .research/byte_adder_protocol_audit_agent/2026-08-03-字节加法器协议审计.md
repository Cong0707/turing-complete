# 字节加法器协议与当前版本许可审计

## 2026-08-03 / 结论纠错

本报告以用户在 **Turing Complete 2.1.281** 中的实机结果为最高优先级：

> 在 `byte_adder`（Adding Bytes）关卡内，原生 kind `30` `com_add` 不能放置。

因此，先前根据 `get_budget` 的中间反编译路径推断“通关后重玩可使用
`com_add`”是错误结论，现已完整撤回。当前研究与候选必须遵守以下边界：

- `com_add` 是完成 Byte Adder **之后**解锁的原生元件；
- 它不能反过来作为当前版本 Byte Adder 自身的合法解法；
- 仓库当前 `154 / 4 / 616` 候选不使用 `com_add`，符合这一边界；
- 公开榜的 `103 / 5 / 515` 只能记为历史榜单事实，不能证明当前版本允许
  `com_add`，也不能据此断言榜单电路的真实拓扑。

当前仓库候选：

```text
SHA-256 cd56a9245cbd12e83673eaf51665807583871bb61337dc4c186331919c22211a
154 gate / 4 delay / 616 energy
原生 com_add 数量：0
```

该候选来自公开 Hub79 的纯门级三态加法器，已离线通过完整真值、Z 冲突、
连通性、v15 往返与精灵几何审计；是否形成当前账号成绩仍以游戏实机验收为准。

## 关卡元数据与可靠解锁边界

当前安装版 `campaign/byte_adder/meta.txt` 为：

```text
kind = combinational
hint_kind = combinational
size = 55
unlocks_components = [com_add]
```

`parse_level_text__modelZcampaigns_u144` 的字段偏移已经静态恢复：

| 关卡记录偏移 | 字段 |
| ---: | --- |
| `+280/+288` | `unlocks_components` |
| `+320` | `components_available` |
| `+384/+392` | `remove_components` |

Byte Adder 没有显式 `components_available`，也没有显式 `remove_components`。
这意味着其菜单不是由该文件中的固定白名单直接给出，而是由 campaign 进度、
全局预算、自定义预算和最终合法性检查共同生成。

能可靠确认的解锁顺序只有：

1. 玩家先使用此前已解锁的基础元件完成 Byte Adder；
2. 完成事件读取 `unlocks_components = [com_add]`；
3. `com_add` 从此供后续关卡或架构使用；
4. 当前 2.1.281 实机仍不允许把它放回 Byte Adder 自身。

因此，Byte Adder 的安全综合集合应限定为**进入本关之前已经解锁且在本关菜单
实际可见的元件**。本报告不把未完整恢复的菜单表擅自写成精确白名单；唯一已经
由实机确认的硬排除项是 kind `30` `com_add`。

## 为什么反编译中间路径不能推翻实机

### 已确认的调用链

`load_level__modelZutilities_u7564`（`0x1405a19fb`）会：

1. 调用 `get_completed_levels__modelZutilities_u6010`；
2. 把完成集合传给 `get_budget__modelZboardZschematics_u2168`；
3. 再由 presenter 刷新组件菜单与自定义组件预算。

`get_budget__modelZboardZschematics_u2168`（`0x140282a68`）内部可见：

- `components_available` 非空时可以直接作为基础预算；
- 某些路径会遍历已完成关卡的 `unlocks_components`；
- 最后会按 `remove_components` 删除条目。

这只能证明“完成状态参与预算计算”，不能证明中间表中的每个条目最终都会在
当前关卡菜单出现，更不能证明编译器会接受它。尚未闭合的后续边界包括：

- `reload_component_menu_budget__presenterZutilities_u13023`；
- `get_custom_budget__presenterZutilities_u6825`；
- `add_component__presenterZutilitiesZhelper95functions_u5957`；
- 编译器对直接元件与自定义元件依赖的最终许可检查。

运行版确实包含两条拒绝信息：

```text
<Component> is not unlocked in this level.
<This custom component> uses a {name} component not unlocked in this level.
```

当前 IDA 数据库尚未恢复它们的完整引用链。用户实机已经证明：至少对 Byte
Adder 的 kind `30`，最终菜单/许可层会排除它。因此此前把 `get_budget` 的一个
completed-level 遍历直接等同于“本关可放置集合”属于证据越级。

## 公开 `103 / 5 / 515` 的正确解释

2026-08-03 抓取的公开榜页面仍保留四个 `103 / 5 / 515`：

- Patchouli
- FermiEnergy
- AidanMars
- zagadka m

这是可复核的历史榜单事实，但页面不公开：

- 电路文件；
- 提交时客户端版本；
- 当时的关卡许可表；
- 当时的递归元件成本；
- 服务端是否重新验证过旧成绩。

因此不能把 `103/5/515` 写成“一个当前版本原生 `com_add` 的已认证解”。当前
证据只支持以下弱解释，并且无法在现有资料中区分：

1. 旧版本曾允许同关卡解锁元件用于重玩；
2. 旧版本的递归/自定义元件成本规则产生了同样的计分；
3. 排行榜保留了版本迁移前的历史成绩；
4. 榜单电路采用了未公开、但门数恰好相同的其它结构。

运行版的动态成本链说明前两种历史机制在工程上并非空想：

- `complete_level__modelZutilities_u8913`（`0x1405a53ef`）遍历
  `unlocks_components` 并调用 `add_cost__modelZscores_u2110`；
- `process_network_responses__presenterZutilities_u38439`
  （`0x14065403f`）会调用 `import_costs__modelZscores_u2127` 导入网络成本。

但这些函数只解释“成本表会动态变化”，不能证明当前 Byte Adder 的放置许可。

## 完整测试协议

固定接口如下：

| 名称 | 方向 | 位宽 | permanent ID |
| --- | --- | ---: | ---: |
| `A` | 输入 | 8 | 1 |
| `B` | 输入 | 8 | 4257300573296473173 |
| `Carry in` | 输入 | 1 | 2 |
| `Output` | 输出 | 8 | 3 |
| `Carry out` | 输出 | 1 | 2340322686578998678 |

`test.si` 对 `tick = 0..131071` 生成输入：

```text
x = tick
x ^= x << 6
x ^= x >> 11
x ^= x << 9
A        = x[7:0]
B        = x[15:8]
Carry in = x[16]
```

独立 GF(2) 审计得到映射秩为 `17`，所以 131072 拍恰好覆盖全部
`U8 × U8 × U1` 输入，无缺失、无重复：

```text
输入序列 SHA-256
2fd98014c77e2d2e05cc92dfa85f9a4a155c0644ae9554967f34dffae6328605

输出序列 SHA-256
a39a167788e2c5acf49f9ff73b5296c77e50e28d239915e02a978ea0ece3ae87
```

期望值严格为：

```text
sum       = A + B + Carry in
Output    = sum & 0xff
Carry out = sum >> 8
```

因此不能依靠测试子集、短周期重放或忽略某些输入组合来压缩逻辑。

## 当前合法基线

当前 `examples/byte_adder/candidate/circuit.data` 不含 kind `30`，组件成本为：

| 元件 | 数量 | 单件门数 | 合计门数 |
| --- | ---: | ---: | ---: |
| Bit Switch | 49 | 2 | 98 |
| AND | 12 | 1 | 12 |
| NAND | 2 | 1 | 2 |
| OR | 16 | 1 | 16 |
| NOR | 25 | 1 | 25 |
| NOT | 1 | 1 | 1 |
| 总计 | | | 154 |

离线证书确认：

- 131072/131072 真值通过；
- 18 个三态 BUS 无 `0/1` 驱动冲突；
- `Output` 与 `Carry out` 全局延迟均为 4；
- 不支持元件为 0；
- 元件实体重叠、导线穿件、导线穿非端点引脚均为 0；
- v15 编解码往返一致。

它是当前版本可继续优化的正常门级基线，而不是利用旧许可或动态成本的历史解。

## 证据等级

### A 级：当前实机

- 用户在 2.1.281 中确认 Byte Adder 不能放置 `com_add`。
- 该结果覆盖任何与之冲突的静态推断。

### B 级：当前安装资产与反编译

- `meta.txt` 证明 `com_add` 由 Byte Adder 完成事件解锁。
- 字段映射证明 `unlocks_components`、`components_available`、
  `remove_components` 是三套不同语义。
- 动态成本链存在，但不能替代最终许可链。

### C 级：公开与持久状态

- 公开榜存在四个历史 `103/5/515`，但拓扑和提交版本未知。
- `levels.txt` 的 `"byte_adder",true,"Default",` 只证明关卡完成，不证明
  当前版本允许把其解锁元件用于自身。

### D 级：候选与离线证书

- `154/4/616` 纯门级候选已通过离线协议与几何检查；仍需游戏内重算确认。

## 后续开发规则

1. 不再部署或推荐含 kind `30` 的 Byte Adder 候选。
2. 排行榜 `103/5/515` 只作为待恢复的历史前沿，不作为当前合法元件证明。
3. 优化应继续研究三态 Switch、联合 carry 状态编码、前缀结构与跨位共享。
4. 每个候选必须完成 131072 全域重算、Z 冲突、全局延迟、v15 往返和布局审计。
5. 只有用户在当前游戏内验收通过后，才能把候选标为“实机通过”。
