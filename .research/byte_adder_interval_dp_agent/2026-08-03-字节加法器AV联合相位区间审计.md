## 新状态：`A=AnyGenerate` 与 `V=F(1)`

对一个连续区间的进位转移函数 `F(c)` 定义：

```text
A = 区间内至少一位 generate
V = F(1)
```

对 low/high 相邻区间，严格有：

```text
Aout = Ah OR Al
Vout = Vh AND (Ah OR Vl)
```

证明要点：若 high 区间本身在 carry=0 时生成，则 `Ah=1` 且结果由 `Vh` 决定；否则 high
区间只有在 low 的 `V` 为 1 时才能得到 `Vh`。因此快速 `Vout` 可物化为同一条 BUS：

```text
Switch(enable=Ah, data=Vh)
Switch(enable=Vl, data=Vh)
```

两个 driver 共享相同 data，重叠时不会冲突；二者只属于这一条 `Vout` BUS。`Aout` 另用一只
OR，所以完整快速 black cell 为真实 `5 gate / 1 delay`。

实际 carry 也满足：

```text
Cout = V AND (A OR Cin)
```

快速 gray cell 使用两只同 data=`V` 的 Switch，真实成本为 `4/1`。普通 black/gray 分别为
`3/2`、`2/2`。

### 每位 Sum 壳

每位同时生成：

```text
G = AND(Ai,Bi)       # A leaf, d1
K = NOR(Ai,Bi)       # d1
P = NOR(G,K)         # d2
V = OR(Ai,Bi)        # V leaf, d1
S = XOR(P,Ci)        # 3 gate / 2 delay
```

即 `7 gate/bit`，八位固定 56 门。这个壳让 A/V 两轨都在 d1 到达，明显快于传统 GP 状态中
d2 才到达的 `P`，因此是值得严格封闭的候选结构族。

## 精确离散求解器

新增：

```text
.research/byte_adder_interval_dp_agent/av_joint_interval_dp.py
```

求解流程：

1. Python 穷举每个连续区间实际可达的 `(A arrival,V arrival)` 状态；
2. 同一区间最多物化一个命名状态和一条确定 recipe；
3. 多个 carry 可以共享该区间的真实 Factory 节点；
4. Z3 选择八条 carry edge，并按 recipe 与 edge 的真实加权成本求解；
5. SAT 后重建完整 Factory DAG；
6. 对全部 `2^17=131072` 输入重放 Boolean value、driven 与 conflict；
7. 每个 BUS 在 DAG 中记录唯一 `resolved_network` owner；
8. Cout 若为 Z-zero，可经过公开 Hub79 已使用的免费
   `Maker2(in1)->Splitter2(out1)` 适配器主动驱动零。本轮正向点的 Cout 在适配前也没有 Z。

模型规模：

```text
interval states    230
interval recipes  1546
carry edges          88
```

求解峰值远低于 1 GiB；两个边界都在 0.1 秒内返回。

## 四延迟边界

在该族内，Sum 固定使用 `3/2` XOR，因此 `C1..C7` 必须不晚于 d2。第一位 carry 可用 A/V
fast gray 在 d2 形成，但 `C2` 的最早到达已经是 d3，所以该族在 D4 的时序状态直接为空。

```text
av_d4_g128.json: UNSAT（empty carry arrival state）
```

这不是 `<=128/4` 的全局下界；它精确说明四延迟必须把 Sum 与 carry 合成最后一层 mux/BUS，
不能保留两延迟 XOR 外壳。

## 晚到双轨两位宏尝试

随后用物理 net-partition SAT 编码尝试：

```text
Cin/~Cin arrival 4
Sum0, Sum1, Cout, ~Cout deadline 6
gate <=24
14 component slots
```

30 秒限制到达后底层 CaDiCaL 没有及时响应 Python 的中断线程；外部命令在约 54 秒被结束。
本轮只终止了命令行明确指向
`late-dual2-cin4-g24-d6-n14.json` 的两个 Python 进程，峰值工作集约 111 MiB。没有输出半写
JSON，严格状态为 **UNKNOWN**，不能写成 UNSAT。

一个不依赖 SAT 的物理合法代数上界是 30 门：低位 Sum 用 `3/2` XOR，两个 carry rail 各用
独立两-Switch BUS，高位 Sum 用双轨两-Switch mux，末端再产生双轨 Cout。它仍太贵，说明
下一轮必须跨 Sum/carry 输出共享普通相位节点，而不是逐输出放独立 mux。

## 结论与下一搜索点

- `A/V` 是物理合法且叶到达早的区间编码，但单独配合 XOR Sum 的严格最优只有 `109/6`。
- `<=85/6` 必须至少改变一项：联合 Sum/carry 相位、多输出共享的强制相位节点，或允许同一
  区间为不同输出保留不同实现并按真实节点并集选择。
- `<=128/4` 必须把最终 Sum 写成一层 BUS/mux；任何先物化 carry、再接 `3/2` XOR 的族都
  在时序上不可能。
- 下一次最小而关键的 SAT 点仍是两位
  `Cin/~Cin@4 -> Sum0/Sum1/Cout/~Cout@6`，但应按 components 与 Switch 数分层，并由外部
  硬超时管理，避免再次等待底层中断。
- 更有价值的全局 DP 状态应同时保存：`C/~C` 两轨、Sum 的 P/NP 相位、BUS owner、全局节点
  mask，而不是先独立优化 carry。
