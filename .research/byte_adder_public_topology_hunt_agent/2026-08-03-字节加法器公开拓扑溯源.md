## `154 / 4` 的完整公开拓扑

公开来源是游戏的 SchematicHub 只读接口：

```text
endpoint      turingcomplete.game:5005
list request  kind 4
item request  kind 5, hub_id 79
name          4d 8bit adder
author        zagadka m
description   Optimized 4d 8bit adder by zagadka m & FermiEnergy & Patchouli
```

本目录保存的精确文件：

```text
hub-79-public/circuit.data
SHA-256 79615b3a78e4824f8b4c4973c69cc76d972745cd5283183d698b1a14206e422d
```

可验证组件账本：

| 元件 | 数量 | 单件门数 | 门数 |
|---|---:|---:|---:|
| Bit Switch | 49 | 2 | 98 |
| AND | 12 | 1 | 12 |
| NAND | 2 | 1 | 2 |
| OR | 16 | 1 | 16 |
| NOR | 25 | 1 | 25 |
| NOT | 1 | 1 | 1 |
| 合计 | | | 154 |

核心不是普通 Kogge-Stone，而是 18 条多驱动三态总线：49 个 Bit Switch 关闭时输出 Z，
同时开启的驱动只要数值一致就不会冲突。17 条总线至少由两只 Switch 合并；`S3..S7`
分别由三只 Switch 直接汇合，`Cout` 由两只 Switch 汇合。该网表的输出深度均为 4。

`hub-79-public/audit.py` 与 `certificate.json` 给出以下可重放结论：

- 穷举 `A:U8 * B:U8 * Cin:U1` 的全部 131072 个输入；
- `sum == (A + B + Cin) & 0xff`；
- `cout == (A + B + Cin) >> 8`；
- 全部多驱动网络的 0/1 冲突数为 0；
- Sum 和 Cout 的复算深度均为 4。

复现命令：

```powershell
$env:PYTHONPATH='src'
.\.venv\Scripts\python.exe `
  .research\byte_adder_public_topology_hunt_agent\hub-79-public\audit.py
```

验证器只读取同目录的 `circuit.data`，因此该证书目录可独立复算；这份文件与仓库已有的
Hub 79 公开归档逐字节相同。

## `103 / 5` 的可重建拓扑

当前版本的原生 U8 `com_add` 精确计分为 `103 gate / 5 delay`。仓库现有只读见证：

```text
examples/byte_adder/candidate/circuit.data
SHA-256 6acfc377ce6fa1a07aa9d91732217ecc1ac4c7d329097be102c49eaa14bfdb6f
```

该见证只有 6 个组件、5 条线：

```text
kind 30  com_add   x1
kind 61  inputs    x3
kind 69  outputs   x2
```

因此一个可精确重建的 `103/5` 拓扑就是：`A、B、Cin -> U8 Add -> Sum、Cout`。
官网恰有四名独立玩家提交完全相同的 `103/5/515` 指纹，和原生组件成本严格吻合。
不过官网没有公开这些提交的 `circuit.data`，故“这四份一定逐字节都是单个 com_add”仍是
高置信推断，而不是公开原件证明。

### Hub 88：完整 `56/18` 低门基线

Hub 88 没有自定义依赖，门数恰好是：

```text
16 AND + 8 OR + 32 NOR = 56 gate
```

这等价于八个平均 `7 gate` 的共享全加器切片：每位 2 AND、1 OR、4 NOR，串行 ripple
得到 18 延迟。它的作者是 SYSTEM-PSD，不是 FermiEnergy；因此它能校准公开 `56/18`
低门端点，却不能证明 Fermi 的中间 Pareto 网表。

位并行证书一次覆盖全部 `2^17=131072` 输入，Sum、Cout 全正确，冲突数为 0，两个输出
复算深度均为 18：

```text
.research/byte_adder_public_topology_hunt_agent/audit_hub88.py
.research/byte_adder_public_topology_hunt_agent/hub-88-certificate.json
SHA-256 fce6f6c4eef5ded29fd9b3ba76227c7379400db32e9823eb682beabda225bc66
```

### Hub 19：没有隐藏的门级 U8 子电路

Hub 19 是一个 v14 32 位 carry-select 包。它放置了 8 个 `kind 30` U8 Add、4 个 U8 Mux
和切分/拼接元件；八只 Add 每只都序列化了 `cost_gate=154`、`cost_delay=4`。包内没有
依赖，也没有自定义 U8 加法器文件。因此它提供的是另一个 `154/4` 成本旁证，而不是可拆解
的四延迟门级拓扑。不能从这八个黑箱反推出 Hub 79 或合作组的内部网络。

### Hub 55：真实但被支配的层级 CLA

Hub 55 包含 15 个依赖和 1 个主文件。主电路门数可严格分解为：

```text
CLA_CORE_8B  172/9
FA_NCout       7/4 × 8
main         228/9
```

CLA core 又递归使用两输入/三输入 AND、OR 以及 4..9 输入归约子元件；全部递归门数与头部
一致。它证明一个真实的层级 U8 CLA 结构，但 `228/9` 被公开前沿完全支配，不能直接用于
排行榜方案。

Hub 59 只有 U4 输入；Hub 225 只有比较器。二者都不再作为 U8 加法器候选继续追踪。

## 公开 GitHub 存档扫描与许可证边界

`scan_public_byte_adder_saves.py` 扫描 6 个公开仓库工作树中的当前 Byte Adder 文件与备份，
共得到 53 条记录，格式只包括 v6、v10、v13。没有命中当前目标 `103/5`、`91/6`、
`88/6`、`79/7` 或 `154/4`；旧版本成绩也不能与 v15 直接比较。

```text
public-byte-adder-save-scan.json
SHA-256 b4d8f32a59499bd0a917871af7f690924586595f939fa5b75acc5097a157623b
```

许可证分布：

- `zoickx/turing-complete`：18 条，`CC0-1.0`；包括旧版 `88/80`、`96/36`、
  `139/20` 等参考文件；
- `chastitywhiterose/Turing-Complete`：6 条，`GPL-3.0`；只作研究证据，不能直接混入
  当前 MIT 项目；
- 其余四个仓库共 29 条，没有明确许可证，只记录哈希与结构，不直接复制实现。

公开 SchematicHub 的上传约定为 CC0；旧 Hub 归档的公开说明明确记录“上传到 Hub 即同意
CC0”，游戏分享界面审计也指向 CC0。因此 Hub 79、Hub 88 等公开分享电路可以作为可复算
研究基线。仍应保留作者、Hub ID 和原始哈希，不把公开来源改写成项目原创。
