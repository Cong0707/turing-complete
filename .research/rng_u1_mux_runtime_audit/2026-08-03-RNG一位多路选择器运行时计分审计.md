# RNG 一位多路选择器运行时计分审计

## 结论

`350 / 10 / 67` 的 RNG 一位 MUX 候选不能作为正常前沿落地。候选的逻辑与版图可以成立，
`com_mux` 在 RNG 中也没有被关卡禁用；失败点是成本账本。

当前游戏档案导入的是：

```text
byte_mux = 34 / 3
```

当前 `2.1.281` EXE 对 `kind 42` 的一位版本应用整数缩放分支，得到：

```text
U1 MUX = 6 gate / 3 delay
```

因此 34 个 U1 MUX 不能按 `34 gate` 计，而应按 `204 gate` 计。候选的运行时预测为：

```text
原账本：350 / 10 / 67 = 234500
修正后：520 / 10 / 67 = 348400
已实机正常前沿：402 / 9 / 67 = 242406
```

修正候选比 `402 / 9 / 67` 多 `105994` 能耗，必须停止沿用这份 MUX 账本。

## EXE 公式

反编译函数：

```text
get_gate_cost__modelZscores_u2232 @ 0x0000000140275f1b
get_delay_cost__modelZscores_u2270 @ 0x0000000140276fb1
```

`kind 42` 的 gate 公式为：

```text
q = imported_gate div 8
r = imported_gate mod 8

if r > 3:
    gate = (q + 1) * word_size + r - 8
else:
    gate = q * word_size + r
```

代入 `imported_gate = 34`：

```text
q = 4
r = 2
U1 gate = 4 * 1 + 2 = 6
```

`kind 42` 命中 delay 的直接返回位掩码，故 `U1 delay = imported_delay = 3`。

这也给出当前 `byte_mux 34 / 3` 下的一般成本：

```text
U1  =  6 / 3
U2  = 10 / 3
U3  = 14 / 3
U4  = 18 / 3
U5  = 22 / 3
U6  = 26 / 3
U7  = 30 / 3
U8  = 34 / 3
```

## 候选状态边界

- `com_mux/kind 42` 本身应可在 RNG 关卡使用；这不是“组件被禁用”的问题。
- 候选已有的连通性、组合环、位宽、Z 传播和版图验证仍然有参考价值。
- `350` 只来自错误的 `U1 MUX = 1 gate` 假设；它不能通过服务端重算。
- 正式文件当前 `custom_id = 0` 且无 512 字节 design。它是独立 v15 电路，能否保持架构身份与
  提交关联属于另一项运行时风险，不能从离线解码直接下结论。
- 后续 RNG 搜索应回到高阻开关的原生结构，或使用明确经过当前 EXE 公式重算的元件；不得再
  把 `byte_mux` 的总 gate 数除以 8 当作一位成本。

## 复现

脚本只读游戏文件和存档，绝不启动游戏，也不修改正式存档。唯一写入是同目录的
`result.json`：

```powershell
cd D:\Develop\Other\turing-complete
.\.venv\Scripts\python.exe `
  .research\rng_u1_mux_runtime_audit\audit_u1_mux_runtime.py
```

脚本会断言：

1. EXE 和反编译证据哈希未变化。
2. `levels.txt` 仍记录 `byte_mux 34 / 3`。
3. 正式文件和候选逐字节一致。
4. 候选恰有 34 个 `word_size=1` 的 `kind 42`。
5. 运行时公式算出 `U1 MUX = 6 / 3`。
6. 修正成绩严格等于 `520 / 10 / 67 = 348400`。

如游戏升级、导入前沿改变或文件被重新保存，脚本会主动失败，避免把旧证据误用于新运行时。
