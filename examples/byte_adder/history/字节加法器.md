# 字节加法器

## 2026-08-01 / 候选构建

### 思路

当前版本的原生 U8 加法器同时提供 `carry_in`、8 位和输出与 `carry_out`，可以直接
覆盖旧的八级全加器链。候选保留关卡的三个输入和两个输出，只替换可编辑区域。

### 修改点

- 在 `(0, 0)` 放置一个 `com_add`（kind `30`，U8）。
- 分别接入 Carry in、A、B，并从原生元件输出接到 Output、Carry out。
- 所有线路只在端点触及元件引脚；导线之间的交叉不作为连接点。

### 离线验证

- 穷举 `A(256) * B(256) * Carry in(2) = 131072` 组输入。
- 每组均比较低 8 位和与第 9 位进位。
- v15 编解码往返、引脚连通性、组件实体碰撞和引脚穿越审计均通过。

候选成绩头为 `103 gate / 5 delay / 515 energy`，仍待游戏内实际验收。

## 2026-08-03 / 研究：建立字节加法器可信边界与公开前沿

### 提交

`研究：归档字节加法器协议与公开拓扑基线`

### 协议与测试边界

- 官方测试覆盖完整的 `A:U8 × B:U8 × Cin:U1`，共 `131072` 组输入；不存在
  可用于样本特化的缺失输入。
- 当前账号的 `levels.txt` 只有关卡完成标记，`byte_adder` 成绩前沿仍为空。
- 已完成关卡的 `unlocks_components` 会进入运行时预算，但电路文件头本身不能伪造
  元件成本；服务端仍会接收实际电路并重新计算。
- 因此，现有单个 `com_add` 文件只是待验收基线，不能把序列化的 `103/5` 直接写成
  当前账号已经认证的成绩。

### 公开电路与前沿

官网和个人页确认了以下公开权衡链：

```text
56/18, 57/17, 59/16, 61/15, 62/14, 63/13, 65/12,
67/11, 68/10, 71/9, 74/8, 79/7, 88/6, 103/5, 154/4
```

其中目前能取得完整网表并独立复算的端点是：

- Hub 88：直接门级 ripple，`56/18`，全 `131072` 输入通过；
- Hub 79：49 个 Bit Switch 与 56 个普通门，`154/4`，全输入通过，18 条三态
  多驱动总线无任何 0/1 冲突。

`88/6`、`79/7` 等中间拓扑仍没有公开原件，不能仅凭排行榜数字虚构电路。

### 已排除的误判

- 对 Hub 79 每条 BUS 独立替换得到的“`131/4`”只是冻结输入到达时间的局部账本。
- 完整 backward slice 和真实递归时序复算表明：保持四级延迟时只有原始
  `154/4` 组合可行；局部替换的真实前沿为 `142/5`、`126/6`、`117/7`，均不能
  击败 `515`。
- 常规 ripple、Brent-Kung、Kogge-Stone、Sklansky、Han-Carlson 与 carry-select
  共审计 2177 个结构，最好为 `75/10/750`，没有低于 `515` 的候选。

### 下一步

1. 把已验证的 Hub 79 手工电路转换成主线 Byte Adder 接口，建立当前账号首个
   可重算的 `154/4` bootstrap 前沿；
2. 用三态转移双轨 `K=00 / P=01 / G=11` 重建公开权衡链；
3. 优先寻找 `<=102/5` 或 `<=85/6` 的完整 DAG；
4. 任何候选必须同时通过全真值、Z 冲突、全局到达时间、v15 往返和真实精灵几何审计。
