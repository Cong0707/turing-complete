# 随机数生成器

## 2026-08-01 / 提交：研究：建立三十二位异或移位专用网络

### 结论

本关应当使用只服务于测试脚本的 32 位线性反馈 ASIC，不应使用、修复或优化
`OVERTURE`、`LEG`、`Overture`、`RV64` 或任何通用处理器。当前 `RV64` 基线为
`235437 gate / 2773 delay / 1440 cycle`，与公开榜首
`431 / 9 / 66 / 256014` 相差数个数量级，继续优化取指、译码、寄存器堆或 ISA 没有意义。

推荐先复刻公开榜首对应的 66 周期结构：一个初始化控制位、32 位状态、固定布线移位和
三层 XOR 反馈。之后再单独研究 65 周期首拍旁路，不要让旁路增加榜首方案的关键路径。

### 判定语义

证据来自最新版 2.1.281 的只读文件：

- `D:\Game\Steam\steamapps\common\Turing Complete\campaign\rng\meta.txt`
- `D:\Game\Steam\steamapps\common\Turing Complete\campaign\rng\test.si`

测试随机选择一个 `1..0xfffffffe` 的非零 32 位初始种子，然后连续检查：

```text
t1 = (seed xor (seed lsr 13)) & 0xffffffff
t2 = (t1   xor (t1   lsl 17)) & 0xffffffff
y  = (t2   xor (t2   lsr 5 )) & 0xffffffff
seed = y
```

`count` 初始为 0，在检查 `count == 64` 时获胜，因此必须按顺序提交 65 个正确结果。测试
没有要求执行程序、保留通用架构状态或支持别的输入协议。公开前缀中的最少周期为 65，
所以周期严格下界为 65；66 周期方案只浪费一个初始化拍，但有更低的门数与延迟乘积。

可用于离线复核的前几项为：

| 初始种子 | 第 1 项 | 第 2 项 | 第 3 项 |
| --- | --- | --- | --- |
| `00000001` | `00021001` | `21211091` | `12828955` |
| `00000002` | `00042002` | `42403122` | `0424023a` |
| `12345678` | `996cc1e4` | `880f6ad6` | `dbbba3f8` |
| `ffffffff` | `f807c000` | `ffbfe03f` | `c219dd2e` |

三次变换都是 GF(2) 上的可逆线性映射，组合矩阵秩为 32。因此非零种子不会进入零状态，
但本方案不依赖把零值当作初始化标志，避免把数据与控制耦合。

### 直接线性网络

固定移位不能使用通用桶形移位器。将 32 位字拆成单比特线后，只为实际发生变化的位放
XOR，其余位直接连线：

| 阶段 | 需要 XOR 的输出位数 | TC 单比特 XOR 成本 | 延迟 |
| --- | ---: | ---: | ---: |
| `x xor (x >> 13)` | `32 - 13 = 19` | `19 * 3 = 57` | 2 |
| `t1 xor (t1 << 17)` | `32 - 17 = 15` | `15 * 3 = 45` | 2 |
| `t2 xor (t2 >> 5)` | `32 - 5 = 27` | `27 * 3 = 81` | 2 |
| 合计 | 61 | 183 | 6 |

按最低位为 `x[0]` 的约定，可直接用下面三组生成式布线：

```text
t1[i] = x[i] xor x[i+13]  , 0 <= i < 19
t1[i] = x[i]              , 19 <= i < 32

t2[i] = t1[i]             , 0 <= i < 17
t2[i] = t1[i] xor t1[i-17], 17 <= i < 32

y[i]  = t2[i] xor t2[i+5] , 0 <= i < 27
y[i]  = t2[i]             , 27 <= i < 32
```

这 61 个 XOR 是规范三阶段分解的精确成本，不是全局最小性声明。无论怎样共享中间量，
32 个输出都不是原始输入或常量，二输入线性直线程序至少需要 32 个新 XOR 结果，即变换
本身有 `96 gate` 的保守下界。最重输出依赖 7 个输入，二输入 XOR 深度至少为 3，按当前
单比特 XOR 的 `delay=2` 计，纯变换延迟下界为 6。

### 候选 A：66 周期低能耗反馈机

状态机语义：

```text
initialized = 0

tick 0:
    state <- initial_seed
    initialized <- 1
    output_enable = 0

tick 1..65:
    next = F(state)
    output = next
    output_enable = 1
    state <- next
```

推荐拓扑：

1. `com_level_input_switched` 只在 `initialized=0` 时驱动状态写入总线。
2. `com_delay_line_bit` 保存初始化控制位；常量 1 接其输入，反相信号控制首拍输入。
3. 反馈结果通过 `com_switch_word` 或 32 个共享控制的 `com_switch_bit`，仅在初始化后驱动
   状态写入总线。
4. 状态输出进入 61-XOR 固定网络；`y` 同时送反馈开关和
   `com_level_output_switched`。
5. `initialized` 直接作为输出有效控制。首拍不提交结果，随后每拍提交一次，共 65 次。

输入和反馈必须是互斥三态驱动，不能把普通输出直接并到同一网络。控制位要放在数据区外，
并让所有反馈开关共用同一条控制网，避免 32 份反相器。

### 排行榜反推

`examples/leaderboard-current.json` 的当前公开前缀给出：

| gate | delay | cycle | energy |
| ---: | ---: | ---: | ---: |
| 431 | 9 | 66 | 256014 |
| 421 | 10 | 66 | 277860 |
| 381 | 11 | 66 | 276606 |
| 448 | 10 | 65 | 291200 |
| 413 | 11 | 65 | 295295 |
| 381 | 12 | 65 | 297180 |

前三个 66 周期点具有同一功能和相邻延迟，最合理的解释是相同 61-XOR 核心配合不同粒度
的状态存储：

- `431/9`：状态拆成单比特低延迟存储，省去状态输出侧的拆分深度。
- `421/10`：部分分组存储，减少 10 gate，增加一层布线/拆分延迟。
- `381/11`：32 位字状态或最低门数存储，减少 50 gate，增加两层拆分延迟。

这三项是根据分数差值和现代元件成本反推的候选解释，并非从榜首电路文件读取。真实元件
组合必须等项目具备时序模拟或人工游戏验收后确认，文档不得把它写成已验证事实。

`431/9` 的关键路径可以由以下结构解释：状态单比特延迟 1、三层 XOR 共 6、两层输出
拼接共 2，总计 9。它也给出该布局下的延迟下界：若输出必须从单比特状态重新组成 32 位
字，`1 + 6 + 2 = 9` 已经不能再压低。

### 候选 B：65 周期首拍旁路

若要达到周期下界，必须在 tick 0 直接计算 `F(initial_seed)` 并提交，同时在之后切到反馈
状态：

```text
current = initialized ? state : initial_seed
next = F(current)
output = next
state <- next
initialized <- 1
```

公开点 `448/10/65` 是优先参考目标。该路线比榜首多 17 gate、关键路径多 1，却只省一个
周期，能耗反而从 `256014` 上升到 `291200`。因此在拿到可工作的 `431/9/66` 前，不应
投入时间优化首拍旁路。禁止在 32 位数据前直接放通用 `com_mux` 后就宣称完成；应比较
三态输入、分组状态和首拍选择是否能把选择逻辑移出三层 XOR 的公共关键路径。

### 布线风险

- 左移 17 和右移 13、5 的位序最容易接反。所有拆分、拼接都统一声明 `bit 0 = LSB`，
  用上述四组种子做逐拍差分。
- `<< 17` 后必须截断到 32 位；不得把高位接回低位形成旋转。
- 输入端与反馈端共总线时只能有一个有效驱动。首拍边界若两端同时有效，会形成多驱动；
  同时无效则状态写入高阻或零，第二拍立刻失败。
- 输出值应当是 `F(state)`，不是旧 `state`。把状态直接输出会整体错一项。
- 初始化控制和数据状态应同拍更新。控制早一拍会丢失初始种子，晚一拍会重复使用初始
  种子。
- 字状态方案的拆分器位宽、分组顺序和额外延迟必须计入关键路径；不能只计算 XOR 深度。
- 自定义 Foundry 封装若用于复用，递归 gate/delay 必须由游戏重新计分，不能信任头部
  声明值。

### 验证计划

1. 离线时序模型先跑固定四组种子，每组至少 65 项，并检查逐拍输出与 Python 参考函数
   完全一致。
2. 随机抽取非零 32 位种子，验证 65 拍内永不使用未初始化状态，且输出使能恰好脉冲
   65 次。
3. 分别统计 61 个 XOR、状态元件、反馈开关和控制元件；门数差异必须能解释
   `431/421/381` 三个目标，而不是手填头部成绩。
4. 检查所有普通网络单驱动，只有输入/反馈汇合网允许三态驱动，并证明控制互斥。
5. 最终人工验收时保持游戏退出，并直接覆盖正式存档中的目标文件；本次研究不启动游戏。

## 2026-08-01 / 提交：优化：逐位状态消除字开关并冲击榜首

### 灵感

公开前沿中的 `381/11/66` 与旧候选 `413/11/66` 正好相差 32 门。结合当前元件成本可反推：
它不是减少了 61 个 XOR，而是用零初态的线性性质替代反馈 Word Switch：

```text
state(0) = 0
tick 0: state <- F(state) OR seed = seed
tick n: state <- F(state) OR 0    = F(state)
```

Architecture Level Input 只在首拍启用；之后其数据值为零。32 个单比特 OR 共 32 门，替代
U32 Switch 的 64 门，所以总门数从 413 降为 381。

进一步把一个 U32 Delay Line 拆成 32 个 Delay Bit。存储门数仍为 `32 * 5 = 160`，但稳定
状态不再经过 `Splitter32 + Splitter8`。输出直接从逐位状态进入三层固定 XOR，再通过两级
Maker 组成 U32；预测关键路径为 `1 + 3 * 2 + 2 = 9`。

- 每一条长反馈线使用独立的左右外侧通道和底部通道，不共享线段，不穿过元件或非目标引脚。

## 2026-08-01 / 提交：优化：复用初始化拍并生成九延迟编码状态机

### 实测反馈与新目标

- 上一版逐位自然状态电路已由人工验收为 `381 gate / 11 delay / 66 cycle`，并到达排行榜第三。
- 它的关键反馈路径是 `Delay Bit(4) + OR(1) + 3 层 XOR(6) = 11`；先前记录中的
  `9 delay` 只是错误预测。
- 新方案不再削减存储门，而是把三层自然状态递推改写成两层编码状态递推，目标为
  `396 / 9 / 66`。

### 状态重编码

令 `A` 为关卡规定的 xorshift32 变换，并在 GF(2) 上定义：

```text
T = (I + R17)(I + R13)
q = T*x
C = A*T^-1
B = T*A*T^-1
```

于是运行拍满足：

```text
visible = C*q = A*x
q_next  = B*q = T*A*x
```

固定的 `B+C` 联合网络只需 `61` 个二输入 XOR，其中第一层 `27` 个、第二层 `34` 个，
最大 XOR 深度为二。初始化拍也没有另建 `T` 网络，而是给这 61 个物理门重新赋予种子线性标签。

### 47 个双模叶子

每个双模叶子是一个单比特 OR：

```text
mode_pair(seed_i, q_j) = seed_i OR q_j
```

- tick 0：32 个状态 Delay Bit 均为零，OR 输出为 `seed_i`，共享 XOR 网络生成 `T(seed)`。
- steady：Architecture Input 已禁用，其数值为零，OR 输出为 `q_j`，同一网络生成 `B(q)`
  和 `C(q)`。
- 固定 61-XOR DAG 下，Z3 已证明至少需要 47 个不同 `(seed_i, q_j)` 配对；生成器恰好使用
  47 个，没有重复放置相同配对。

### 成本与时序

```text
32 * Delay Bit = 160 gate
61 * XOR       = 183 gate
47 * OR        =  47 gate
ready Delay    =   5 gate
NOT            =   1 gate
总计           = 396 gate

反馈关键路径 = Delay Bit(4) + OR(1) + XOR(2) + XOR(2) = 9 delay
周期         = 1 个装载 tick + 65 个有效输出 = 66 cycle
能量         = 396 * 9 * 66 = 235224
```

公开参考榜首为 `431 / 9 / 66 = 256014`。若游戏端重算与离线拓扑一致，新方案能量低
`20790`，并将超过该参考成绩。

### 实现与版图

- 新增 `src/tc_save_lab/rng_encoded_asic.py`，固化 `A/T/B/C`、61 门 DAG、47 个双模配对和
  确定性组件 ID。
- `architecture_candidates` 中的 `rng` writer 已切换到编码状态版本。
- 候选包含 `155` 个组件、`294` 条导线；47 个 OR 贴近唯一 XOR 消费端放置，避免形成高而
  混乱的中央元件列。
- 每条导线以当前元件实体和全部非目标引脚为障碍独立寻路；允许导线互相交叉，但不会穿过
  元件、元件引脚或其它元件的端口走廊。

### 离线验证

- `C*T=A`、`T*C=B`、`T*T^-1=I` 全部成立。
- 69 个确定性 U32 种子逐个验证：tick 0 精确装载 `T(seed)`，随后 65 个输出和每拍编码状态

  7 个 Architecture I/O 面板端口合法出入格。

## 2026-08-02 / 提交：优化：以一位字异或压缩反馈网络

### 灵感

实机已经确认上一版编码状态机实际为 `396 / 10 / 66`。当前 RNG 关卡中，Bit XOR 的成本
是 `3 gate / 2 delay`；将 Word XOR 配置为 `word_size=1` 后，同样执行一位异或，但成本为
`1 gate / 3 delay`。因此不能把 61 个 XOR 无差别替换，否则会抬高可见输出关键路径。

对联合 `B/C` DAG 做精确静态时序约束后，找到 19 个满足以下条件的第二层节点：

- 只参与反馈变换 `B`，不参与可见输出变换 `C`；
- 替换后反馈路径最多从 9 增至 10，而当前可见输出路径仍为 10；
- 每个节点节省 2 gate，合计节省 38 gate。

这 19 个节点按逻辑行和稳定 `permanent_id` 双重固化，生成器不会按元件顺序猜测替换目标。
控制协议同时恢复为实机验证过的全零初态：常量 1 驱动 `ready` Delay Bit，`NOT ready`
只在 tick 0 开启种子输入，`ready` 从 tick 1 起开启唯一输出。33 个 Delay Bit 的
`init_data` 全部为 0，不再使用已经被实机否定的 `init_data=1` 首拍假设。

### 成本

```text
32 * Delay Bit = 160 gate
42 * Bit XOR   = 126 gate
19 * U1 Word XOR = 19 gate
47 * OR        =  47 gate
ready Delay    =   5 gate
NOT            =   1 gate
总计           = 358 gate

预测成绩       = 358 / 10 / 66
预测能量       = 236280
公开榜首参考   = 431 / 9 / 66 = 256014
```
